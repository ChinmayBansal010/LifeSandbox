# Security

Development auth maps requests to `local-user` only while `APP_ENV` is not production. Production mode requires `AUTH_MODE=jwt` and a secret and checks HS256 signature, issuer, audience, expiration and subject. This is a basic adapter, not Better Auth integration or a substitute for production key rotation/JWKS verification. Never deploy the development bypass.

Ownership is derived from the authenticated principal for conversation, memory, candidate, project, task, reminder, job, approval and file lookups; foreign IDs return 404. Local memory saving requires explicit user action or an explicit "remember" request covered by an allowed nonsensitive policy category. Hosted Mem0 use additionally requires persisted permission and per-exchange opt-in. User text, memories and tool results are untrusted.

Approval execution rechecks ownership, approval status, a 24-hour expiry (including legacy proposals without an explicit expiry), and the stored payload hash. Only validated `task.create` and `reminder.create` actions have executors; unknown external actions cannot run. Execution and idempotency state commit together. Audit rows store resource IDs, outcome and correlation ID, not action arguments. Task/reminder tools are owner-scoped, validate linked projects/tasks, and expose no permanent-delete or external delivery tool. Logs avoid request content and exception responses avoid stack details. Upload names reject path separators, allowed MIME types and sizes are checked, keys are tenant-scoped, and URLs expire after five minutes. Upload MIME/size should also be verified at the object boundary before processing (not implemented). Neon Object Storage object cleanup is unfinished.

Google OAuth is optional. Configure the client ID, secret, exact callback URL, and a Fernet key in the server environment. State values are hashed in the database, expire after ten minutes, and are consumed before exchanging the code; callback ownership comes only from that state row. Access and refresh tokens are Fernet-encrypted and never returned by the connection API. Keep the encryption key outside the database and back it up separately. Losing the key requires users to reconnect. Disconnect clears credential ciphertext and attempts provider revocation. Gmail draft sending is available only through an exact-snapshot approval; Calendar event writes remain unavailable even if broader scopes are granted.

Approved Gmail draft sending is bound to the draft ID, connected-account ID, recipients, subject, body, thread, and content hash. The executor re-fetches the draft after approval and refuses changed content, checks the owner's still-connected connection and send scope, claims the action before contacting Google, and persists the returned message ID. A network timeout or server error leaves an `uncertain` status and is not retried automatically. Gmail content is excluded from tool traces; the pending approval itself stores the requested snapshot so it can be reviewed by the owner.
# Plugin catalogue and execution controls

The authenticated plugin catalogue returns tool descriptions, scopes and owner-specific Google connection statuses only; it never includes OAuth tokens, encrypted credentials, API keys or prompts. `connected` means required scopes are persisted on one of the user's connected accounts and is not an upstream health assertion. The user-facing execution history similarly omits tool inputs and outputs.

The model only receives request-relevant tools after Google scopes have been filtered. The dispatcher rejects unknown/unselected tools and validates arguments against the registry schema. Google integrations repeat owner, connection and scope checks in their provider path. Tool/provider output remains untrusted and cannot grant permissions. Gmail send remains a separate exact-payload approval flow; calendar writes are not supported.

Google app sign-in is a separate OpenID Connect flow. It uses owner-independent one-time state bound to a short-lived HttpOnly SameSite=Lax cookie, PKCE, nonce verification, Google JWKS signature checks, verified email, and an eight-hour signed HttpOnly session cookie. The session subject is the stable Google `sub`, namespaced as `google:<sub>`; email is display metadata and never an ownership key. `AUTH_SECRET` signs app sessions and must be set before enabling sign-in. In development, the local `local-user` fallback remains available when no session cookie is present; production requires JWT mode and does not use that fallback.
